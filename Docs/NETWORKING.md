# Сеть и Mirror

Документ описывает текущую сетевую поддержку проекта. Сейчас Mirror используется для запуска сессии, спавна сетевых объектов и синхронизации тайлов грида. Движение игроков и другие игровые состояния этим сетевым слоем пока не синхронизируются.

## Как синхронизируется грид

Сетевой грид состоит из компонентов `NetworkIdentity`, `Grid`, `GridVisual`, `Damageable` и `NetworkGrid`.

- Сервер хранит авторитетное логическое состояние в `Grid`, включая координаты клеток и ненулевые ID тайлов; `Damageable` хранит текущее здоровье каждой повреждённой клетки.
- `NetworkGrid` на сервере подписывается на изменения тайлов и здоровья. Изменения сервер рассылает клиентам через `ClientRpc`.
- Удалённый клиент очищает логические данные своей копии `Grid` и хранит полученные клетки в `GridVisual`. Меши и коллайдеры создаются локально, поэтому по сети не передаются Unity-объекты, материалы или меши.
- При появлении сетевого грида клиент запрашивает начальный снимок. Сервер посылает его этому клиенту пакетами до 512 клеток через `TargetRpc`, включая текущее здоровье. Последующие изменения тайлов и здоровья идут отдельными RPC.
- В режиме Host сервер и клиент находятся в одном процессе: `Grid` остаётся авторитетным, а визуализация работает как на клиенте.
- На server-only объекте `NetworkGrid` отключает `GridVisual`.

Поток изменения клетки:

1. Клиентский ввод определяет координату клетки. `GridClickInteraction` использует raycast и вызывает запрос `NetworkGrid`, если Mirror активен.
2. `NetworkGrid` отправляет серверу запрос установки, удаления или нанесения урона.
3. Сервер проверяет запрос и меняет свой `Grid` или здоровье в `Damageable`.
4. Событие изменения приводит к рассылке; клиенты обновляют `GridVisual`, который перестраивает затронутые чанки.

В одиночном режиме `GridClickInteraction` меняет `Grid` напрямую. При сетевой игре используйте запросы `RequestSetTile`, `RequestRemoveTile` и `Damageable.DamageTile`, а не записывайте данные клиентского `Grid`.

## Настройка

В `SampleScene` уже настроены:

- Mirror `NetworkManager` с `NetworkManagerHUD`;
- `TelepathyTransport` на порту `7777`;
- `GameObject.prefab` как player prefab, с автоматическим созданием игрока;
- `Grid.prefab` в списке spawnable prefabs.

`Grid.prefab` содержит `NetworkIdentity`, `Grid`, `GridVisual`, `Damageable` и `NetworkGrid`. Если добавляете другой сетевой грид, проверьте наличие этих компонентов. Для спавна prefab во время игры он должен быть зарегистрирован в `NetworkManager` и создаваться сервером; сетевой объект сцены должен присутствовать в сетевой сцене и быть распознан Mirror.

Для локальной проверки запустите Host через HUD, затем подключите отдельный экземпляр игры как Client. В конфигурации сцены адрес клиента по умолчанию — `localhost`; для подключения по сети укажите адрес машины-хоста. Клиенты и сервер должны использовать совместимые сцены, prefab'ы и реестр тайлов.

`GameObject.prefab` сейчас содержит только `NetworkIdentity`. Серверная проверка дистанции использует позицию `sender.identity.transform`; игровая система движения должна обновлять её корректно. Само движение этим prefab'ом и описанной синхронизацией не реализовано.

## Серверная проверка запросов

На сетевом объекте `NetworkGrid` доступны настройки:

- `allowClientEdits` — разрешает или запрещает клиентские запросы на изменение клеток;
- `maxEditDistance` — максимальная дистанция от игрока до клетки, минимум `0.1`.
- `RequestDamageTile` проверяет дистанцию и разрешение на редактирование так же, как установка и удаление. Порог минимального урона проверяется по `TileDefinition` на сервере.

Перед записью сервер проверяет высоту клетки, разрешение на клиентское редактирование, наличие player object у подключения, дистанцию до клетки и регистрацию ID тайла. ID `0` зарезервирован для пустой клетки, поэтому его нельзя передавать для установки; удаление выполняется отдельным запросом. Сервер не использует клиентский raycast как доказательство допустимости действия.

`RequestSetTile`, `RequestRemoveTile` и `RequestDamageTile` возвращают `true`, когда запрос может быть отправлен локально; это **не** подтверждение того, что сервер его принял. Сервер отклоняет неправильные запросы и записывает предупреждение в лог. Клиент не получает отдельного результата принятия/отклонения и не применяет оптимистичное изменение до серверного RPC.

Эти проверки не реализуют разрешения на строительство, проверку видимости или ограничение частоты запросов. Если такие правила нужны, добавьте их в серверную проверку `NetworkGrid` до применения изменения.

## Реестр тайлов и совместимость

Сервер и клиенты должны иметь загруженный `TileRegistry` с одинаковым соответствием ID определениям. ID передаются по сети вместо материалов и остаются стабильными для сохранений и совместимого контента. Не переназначайте уже используемые ID другим тайлам.

При применении снимка или изменения клиенту также требуется зарегистрированное локальное определение соответствующего ID, включая визуальные материалы. Автоматической проверки версии/хеша реестра при подключении сейчас нет; несовместимость контента нужно исключить конфигурацией сборок.

## Границы текущей реализации

- Синхронизируются изменения клеток грида, но не движение игрока, создание грида игровым кодом, права доступа, сохранения или прочее состояние мира.
- RPC обновляют визуальные данные; сетевые изменения не являются общим механизмом репликации произвольных полей `Grid`.
- Клиентский запрос не содержит подтверждения результата. UI, которому нужно показывать отказ или ожидать серверное решение, потребует отдельного ответа/протокола.
- `maxEditDistance` ограничивает расстояние до клетки, но не проверяет линию видимости и не ограничивает частоту запросов.
